Screens to add to ShieldMate

Frontend proposal · 1 November 2026 · checked against frontend/src and backend/contract.py as they are today

ShieldMate's 11 screens cover the live moment well: an alert arrives, staff act, the owner decides and IT fixes it. What's missing is before and after that moment. No screen keeps an incident's record once it closes or drafts the CERT-In report. Some backend data has no screen at all. Staff can only react to alerts. This proposes 13 screens: 9 build on today's API, 4 need a small contract addition.

Each mockup is a standalone .html file in this folder. It loads the app's real stylesheet and fonts (frontend/src/styles/shieldmate.css), so it looks like the app; keep the folder where it is. Every mockup ends with build notes covering why, which routes and fields it uses, and what the backend needs. A dashed needs field chip marks a value the API doesn't return yet.

Where they sit

Incident detail also opens from the cards on Right now and from “Closed today”. On phones, the owner's three new menu items go in a “More” tab, and staff get a fifth tab, Help.

Gaps in today's screens

  • An incident's story disappears once it closes. Staff history rows don't open (Staff.jsx:324). Right now keeps 3 closed incidents (OwnerNow.jsx:430) and the newest 7 activity lines (OwnerNow.jsx:471). → Incident detail, History, Staff history.
  • Promised on screen, not built. The CERT-In card says a report will be “drafted from this timeline” (OwnerNow.jsx:295). Readiness says choosing a second person “is part of setup (after the demo)” (OwnerReadiness.jsx:220). “Last month's” drill score is hard-coded sample data (content.js:93). → CERT-In draft, Setup, Practice history.
  • Backend data with no screen. POST /restore/verify is in the contract (contract.py:771), but api.js has no function for it. Device services, blocks and impact show only as a status pill. The practice attack's timing and stages show as one line. → Recovery check, Computers, Debrief.
  • Staff can only react. The language toggle appears only on an alert card (Staff.jsx:104–114). Cards say to call numbers “saved in ShieldMate”, but only IT's number is saved. Three of the five drills start with a call or email a person notices, yet there's no way to report one. → First-run setup, Saved numbers, Report.
  • Fragile edges. If the server is down on first load, screens show “Loading…” indefinitely, under a banner about “the last update”. An unknown address falls through to Start (App.jsx:60). setOwnerPin is never called (session.js:96), so turning on the owner PIN (decision 3) would block every owner decision. → System states.

Screen by screen

1System states and PIN prompt

every screen · everyone
Why
First-load failure, unknown links and the owner PIN have no proper screen.
Shows
Can't reach ShieldMate (Wi-Fi checks, laptop address), unknown person, not found, feature switched off, PIN sheet.
Data
usePoll's error, GET /status flags, setOwnerPin.

2Incident detail

/owner/incident/:alertId · owner
Why
Who did what and when is in AlertOut, but split across cards and gone once closed.
Shows
Checklist with names and times, one-incident timeline, CERT-In clock, computer, IT progress.
Data
Alerts (closed included), actions, latest restore check, activity() for one alert.

3History

/owner/history · owner
Why
Right now keeps 3 closed incidents and 7 events; nothing lists them all.
Shows
Every incident since the last reset, the practice attack, and the full activity log with filters.
Data
What Right now polls; activity() gains a kind and alert id per event.

4CERT-In report draft

/owner/incident/:id/report · owner
Why
Promised on the CERT-In card; the REPORT_CERTIN and START_DPDP_NOTE steps have nothing behind them.
Shows
Fields filled from the incident, gaps for the owner, copy and print, a breach-record tab.
Data
The incident's own data. Nothing is sent from ShieldMate.

5Recovery check

/owner/readiness/recovery · owner

/staff/:id/history · /staff/:id/alert/:id · staff

8Computers

9Practice attack debrief

/owner/practice-attack · owner

10Saved numbers

/staff/:id/help · staff

11Report something suspicious

/staff/:id/report · staff
Why
Phishing, fake tech support and bank-detail fraud start with a person noticing, and there's no way to say so.
Shows
Pick what happened, do-now steps, an optional note, tell Dr. Rao.
Data
New POST /reports that creates an owner notification. The guidance can ship first.

12Setup

/owner/setup · owner
Why
Readiness sends “choosing a second person” to a setup screen that doesn't exist.
Shows
People and cover, who gets which alerts, blocking and timings, backups, IT contact, saved numbers, PIN.
Data
Reads from GET /clinic. The standing rule saves today; the rest needs routes.

13Practice history

/owner/drill/history · owner
Why
Readiness knows only the last drill this device ran; the comparison is sample data.
Shows
All five drills with last run and score, run by run, and habits still to learn.

Smaller additions (no mockup)

  • Owner “More” tab. The owner's phone tab bar has four slots. History, Computers, Setup and “Switch person” go in a More sheet.
  • Staff “Help” tab. A fifth tab means .tabbar needs five columns on staff pages (shieldmate.css:219).
  • Links into the new pages. Turn the practice-attack result, the headlines on Right now, and the device rows into links.
  • Language toggle on Today, not only on an alert card.
  • Judges' mini-drill. Built in the earlier vanilla UI (docs/reference/vanilla-ui/judge.html, judge-tally.html) but never ported. The contract has no routes for it.
  • Ask ShieldMate with a typed question. Already mocked in docs/n8n-help-widget-mockup.html. InterpreterRequest already carries alert_id, drill_code and device_id.
  • IT panel history. The panel shows “Closed today” only.

Open questions

  1. One contract batch? Screens 10 to 13 and the optional fields need contract changes. CLAUDE.md requires all four owners and the contract tests in one merge, so batch them: contacts, the settings and staff writes, the drills list, reports, and the device fields.
  2. CERT-In fields. Check the draft's fields against CERT-In's current incident reporting form before building it.
  3. Patient-data breach record. Confirm with an advisor what it must contain and by when; the mockup shows fields only.
  4. Owner PIN and staff Block buttons. Staff Block taps call approve as the owner. With the PIN on, should they see the prompt, or should the button hide?
  5. Staff reports. Should a report stay a note to the owner, or open a full incident with the IT loop?
  6. Translations. New staff strings need the fluent-speaker check (Testing Plan T2.05) before Kannada and Hindi ship.
