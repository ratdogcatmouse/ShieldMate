# Plan: Real Backup/Restore Verification + Attack Notifications with Quick-Action

Context: two new features for the ShieldMate backend, extending Cetas's lane (`restore/*`,
`demo_backup/*`, routes `restore`) and Ishaan's lane (`alerts/*`, `routes/notifications.py`,
`contract.py`). Locked decisions from the user:

1. **Backup/restore**: the demo *directory* stays synthetic, but the feature must be a real
   working check: snapshot the compromised directory → apply an "update" to the live
   directory → re-scan the updated directory for the *same static vulnerability markers*
   → and run an **optimal recovery test**: restore a known-good backup into a sandbox and
   verify hash-integrity + post-restore marker scan. Fast, deterministic, demo-safe.
2. **Attack notifications**: extend the existing notifications lane (no Web Push — it
   doesn't work on a plain-LAN-IP demo rig). An attack creates a special `attack`
   notification to the *relevant users* (owner + the device's account role), carrying a
   structured **quick-action button** (`BLOCK_IP` for `clinic.block_minutes`, e.g.
   "Block 192.168.1.57 for 60 min") that reuses the existing `POST /actions/{id}/approve`.

---

## Feature 1 — Real backup/restore verification (Cetas)

### Today (why it feels faux)
`restore/checker.py` only checks the synthetic demo backup's freshness/integrity/exposure.
Nothing is ever compromised, nothing is ever *recovered from*, and the "backup" is checked
once by a button.

### Design — `backend/restore/verify.py` (new, ~150 lines, Cetas lane)

New route: **`POST /restore/verify`** (owner, ACTIONS-free, always available). One call
performs the whole story on the demo directories, sandbox-only writes (same rule as T1.14 —
the checker only ever writes `restore_sandbox/`):

1. **Snapshot the compromised stuff.** `demo_backup/compromised/` (a new generated tree:
   ~20 small files, deterministic, some containing **vulnerability markers**) is copied to
   `restore_sandbox/snapshot/` with a SHA-256 manifest *and* a marker report
   (`vuln_found: [{file, marker}]`). This is "backing up the compromised directory".
2. **Update the live directory.** The `demo_backup/patched/` tree (the "patched codebase")
   is applied over `demo_backup/compromised/` — a real copy, not a pretend.
3. **Compare updated vs. backup (same vulnerabilities?).** Re-scan both the snapshot and
   the updated directory with the shared marker list. Report `vuln_before`, `vuln_after`,
   `vuln_fixed`, `vuln_remaining` + file diff. Pass criterion: **`vuln_remaining` is empty
   and `vuln_before` was non-empty** (the patch actually closed the holes that the backup
   captured).
4. **Optimal recovery test.** Restore the *known-good* `demo_backup/originals/` backup into
   `restore_sandbox/recovered/` and verify three layers (all fast, all deterministic):
   - hash-integrity: every file matches its manifest SHA-256 (the existing checker's core),
   - file-set: nothing missing, nothing extra,
   - **post-restore marker scan: the recovered copy is clean of every vulnerability marker**
     (a backup that restores *with* the vulnerabilities still in it fails).
   This layered, sub-second check *is* the optimal way to test backup recovery: it proves
   the backup both round-trips byte-exactly and does not resurrect known vulnerabilities.

Result object `RestoreVerifyResult`:
```json
{"kind": "verify", "result": "PASS|FAIL", "vulns_found": 4, "vulns_remaining": 0,
 "recovery": {"files_total": 20, "files_ok": 20, "markers_in_recovered": 0},
 "checks": [snapshot, update, vuln_delta, recovery], "started_at": ...}
```

### Vulnerability markers (content, deterministic)
`demo_backup/vuln_markers.json`: a short list of literal signatures, e.g.
`"CVE-2026-1101"`, `"MD5_PASSWORD_HASH"`, `"OLD_TLS_CIPHER"`. Compromised files contain 2–3
of them; `patched/` and `originals/` contain none. Scanner is a plain substring search per
marker per file — no runtime, no dependencies, identical on every machine (same rule as
the demo-backup generator's fixed seed).

### Files (Cetas)
- `demo_backup/make.py` — extend `build()` with `compromised/` + `patched/` + `vuln_markers.json`
  (deterministic, `write_bytes`, regenerated by `db.reset` via `ensure(force=True)`).
- `restore/verify.py` (NEW) — `snapshot()`, `apply_update()`, `scan_markers()`, `recovery_test()`,
  `run_verify()` returning the `RestoreVerifyResult` dict; pure functions on config paths so
  unit tests point at temp dirs (same pattern as `checker.py`).
- `routes/restore.py` — add `POST /restore/verify` (owner-gated, thin body).
- `schema.sql` — `restore_runs` gains `kind TEXT NOT NULL DEFAULT 'check' CHECK (kind IN ('check','verify'))`;
  verify results store in the same table (no new tables; `RUNTIME_TABLES` already covers it).
- `main.py` / `db.reset` — nothing needed (sandbox emptied on reset; `make.ensure` regenerates).
- Auto-snapshot on compromise (seam, 1-liner each): when the pipeline creates a `100201`
  (encryption) card, call `restore.verify.snapshot_only(db, clock, config)` — Cetas writes
  the function, Ishaan writes the one-line call in his pipeline. Keeps "backup the
  compromised stuff" automatic instead of button-only.

## Feature 2 — Attack notifications + quick-action button

### Design
- **Relevance**: seed's `impact.device_accounts` already maps device → account role
  (`RECEPTION-PC → front_desk`, `FILE-SERVER → billing`, `DOCTOR-PC → owner`).
  **Relevant users = that role's staff + the owner** (owner is the escalation target,
  decision 16). Pure mapping helper `alerts/impact.py::notify_roles(agent_name, book)` →
  Cetas.
- **Create**: in the pipeline's `created` branch (Ishaan), after the card + proposal:
  `db.add_notification(..., kind="attack", to_role=<role>, action_row_id=<BLOCK_IP row or None>)`
  for each relevant role. No severity filter needed — a *new* attack card is the attack;
  grouped/reopened events don't re-notify (only the `created` path).
- **Quick action**: `POST /actions/{id}/approve` already blocks the IP for
  `clinic.block_minutes` (60) — the button just fires it with `decided_by` = the
  notification's recipient (staff tap). No new action machinery.
- **Contract** (ships with fixtures + contract tests, one merge):
  - `NotificationOut` gains `quick_action: QuickAction | None` where
    `QuickAction = {action_row_id, action: "BLOCK_IP", label, target_ip, minutes, status}` —
    built by the notifications route joining `actions` when `notification.action_row_id` is
    set (it's already a column!); `minutes`/`label` from `propose.label_for` + clinic.
    `target_ip` null (ransomware, no source IP) → no button.
  - `notifications` table gains `kind TEXT NOT NULL DEFAULT 'info' CHECK (kind IN
    ('info','attack'))` — the frontend dims attack notifications and shows the button.
- **Frontend** (Abhiram, thin): attack notification row renders the button; tap →
  `POST /actions/{id}/approve`; on success mark the row "handled" (re-poll shows
  `quick_action.status = "executed"` and disables the button).

### Files (Ishaan)
- `schema.sql` — `notifications.kind` column (+ `db.reset` re-seeds setup tables, fine).
- `db.add_notification(..., kind="info", action_row_id already exists)` — add `kind` param.
- `alerts/pipeline.py` — `created` branch: attack notifications via new helper
  `alerts/notify.py` (Ishaan: orchestration; calls Cetas's `notify_roles`).
- `routes/notifications.py` — join `actions` (when `action_row_id` set, ACTIONS on,
  status `proposed`/`executed`/`expired`) and attach `quick_action`.
- `contract.py` — `QuickAction` + `NotificationOut.quick_action` + `kind` on
  `NotificationOut`; fixtures `notifications.json` (key parity! LANE-1 test) + a new
  extra fixture `notification_attack.json`.
- 1-liner pipeline call: `restore.verify.snapshot_only` on `100201` creation.

### Files (Cetas)
- `alerts/impact.py::notify_roles()` — device → [account_role, "owner"], deduped.
- Everything in Feature 1.

### Files (Abhiram)
- Notification UI: attack styling + button + tap-to-approve + local handled state.
- `backend/.env.example`: document `ACTIONS=1` for the notification demo.

## Tests (gate before commit)
- Cetas: `tests/unit/test_restore_verify.py` — compromised fixture: scan finds N markers;
  verify PASS (patched + good backup); FAIL cases: patch leaves a marker, recovery hash
  mismatch, recovered tree contains a marker. `tests/api/test_restore_flow.py` + verify route.
- Ishaan: `tests/api/test_alert_flow.py` — new card ⇒ one `attack` notification per
  relevant role, `quick_action` present iff a BLOCK_IP proposal exists; ACTIONS off ⇒
  no `quick_action`; grouped/repeat ⇒ no new notification.
- Contract: both fixtures updated in the same merge; LANE-1 key-parity test passes.
- Full suite green: `python -m pytest -q`.

## Build order
1. Cetas: demo dirs + markers + `restore/verify.py` + route + tests (independent, no contract collision).
2. Ishaan: `kind` column + `quick_action` contract/fixtures + pipeline notify + auto-snapshot hook.
3. Abhiram: notification button UI (consumes #2).
4. Demo wiring: `ACTIONS=1`, reset, run sim `ransom_wave` → button blocks the attacker;
   owner taps `/restore/verify` → PASS story.

## Out of scope
- Web Push / service workers (rejected: broken on the LAN demo rig; contract stays
  push-attachable via `quick_action` later).
- Running/vulnerable-code execution ("behavioral" scanning) — static markers only.
- Real lab backups — the feature works on the demo dirs and takes `RESTORE_*` env paths,
  so it *would* work on a real snapshot; that's a config change, not a code one.
